# Состояние проекта codex-limit-bot

## Назначение

Telegram-бот сообщает о пятичасовом и недельном лимитах Codex, порогах остатка, сбросах и временной недоступности данных. Также поддерживаются запрос текущих лимитов и определение часового пояса пользователя.

## Ветки и устройства

- Основная ветка: `main`.
- Рабочая ветка: `dev`.
- Устройства разработки: `windows-pc`, `macbook`.
- Обычная межустройственная синхронизация выполняется через `dev`.
- Публикация в `main` требует отдельного конкретного разрешения пользователя.

## Текущее состояние

- Актуальная версия функций бота объединена в `main`; рабочая `dev` создана от этой версии.
- Согласованная версия исходного кода — **`1.1.1`**. Исторические версии и контрольные коммиты записаны в `CHANGELOG.md`, текущий номер — в `VERSION`. Первый стабильный выпуск ретроспективно определён как `1.0.0`.
- Активный production-экземпляр работает на собственном VPS пользователя, доступном через `ssh my-vps`. На нём развёрнута версия **1.1.1**; GitHub и состояние сервера остаются разными сущностями, пока автодеплой не настроен.
- Бот проверяет лимиты раз в минуту, уведомляет о порогах 20%, 10%, 5% и 0%, сообщает о сбросе и поддерживает команду `/limits`.
- Поддерживаются тихие часы и часовой пояс, определяемый по разово переданной геопозиции.
- Рабочий экземпляр размещён на новом собственном VPS. Подтверждённые компоненты старого экземпляра удалены со старого VPS; чужие службы, VPN и неподтверждённые общесистемные компоненты оставлены.
- Состав выполненной очистки и намеренно оставленные компоненты записаны в `docs/OLD_VPS_CLEANUP.md`.
- В `dev` подготовлена схема CI/CD с immutable releases, точным SHA `origin/main`, restricted SSH, `flock`, атомарным переключением, health check и автоматическим rollback. Она ещё не установлена на сервер и выключена отсутствием `PRODUCTION_DEPLOY_ENABLED=true`.

## Устройство проекта

- Основная логика находится в `bot.py`.
- Шаблоны служб и таймера находятся в репозитории. На активном VPS проект расположен в `/opt/codex-limit-bot`, рабочее состояние — в `/var/lib/codex-limit-bot`, секретное окружение — в `/etc/codex-limit-bot.env`; службы запускаются от пользователя `codexbot`.
- Автоматические проверки находятся в `tests/`.
- Секреты, авторизация Codex и рабочие файлы состояния VPS в Git не входят.
- Архитектура и ручная подготовка production описаны в `docs/DEPLOYMENT.md`; deploy-скрипты находятся в `deploy/`, production-зависимости зафиксированы в `requirements.lock`.

## Проверки

- Перед созданием `dev` актуальная версия уже была объединена в `main` коммитом `86d4a2f`.
- На новом VPS проверены Telegram listener, минутный timer, `/limits`, обновление часового пояса, разовая серверная отправка лимитов и восстановление после перезагрузки.
- На старом VPS рабочий экземпляр остановлен и отключён, чтобы исключить двойную обработку Telegram-команд и уведомлений.
- После очистки на старом VPS проверено отсутствие units, процессов, выделенных путей, пользователя и группы `codexbot`; новый production VPS остался активен и успешно выполняет минутные проверки.
- В рамках настройки синхронизации меняется только документация, поэтому тесты кода повторно не запускались.
- На Windows проверены наличие командных правил, файла состояния и корректность изменённой документации.
- При отправке `dev` проверяются совпадение локальной и удалённой вершины и чистота рабочей копии.
- Реальный двусторонний цикл через MacBook пока не выполнен.
- После полного ревью CI/CD на Windows прошли 23 unit tests, `compileall`, Bash syntax check, ShellCheck 0.11.0, YAML parse, `git diff --check`, положительная и отрицательная проверки systemd policy, сверка lock-файла и проверка Linux wheel hashes. Безопасный health check проверяет Codex, Telegram bot и целевой chat без отправки сообщений; production listener дополнительно проходит десятисекундную проверку стабильности. `visudo` и `systemd-analyze` локально недоступны; обе проверки добавлены в GitHub CI, а `systemd-analyze` также выполняется deploy-скриптом до изменения служб.

## Следующий шаг

Текущий production-target для серверных действий — только новый собственный VPS через `ssh my-vps`. Следующий этап после проверки и публикации подготовительных файлов в `dev` — отдельно разрешённая ручная установка схемы из `docs/DEPLOYMENT.md`, настройка GitHub Environment/Secrets и финальное включение repository variable. До этого push в `main` production не обновляет.

## Ограничения и риски

- Отправка коммитов в GitHub не обновляет работающего бота.
- Нельзя запускать локальный Telegram listener с рабочим токеном одновременно с серверным listener.
- Нельзя помещать в Git токены, файлы авторизации, локальные состояния или содержимое `.codex`.
- До настройки согласованного автодеплоя нельзя вручную обновлять или останавливать рабочий бот на новом VPS без отдельного разрешения.
- Lock-файл рассчитан на CPython 3.12 и Linux x86_64; смена платформы требует его осознанной пересборки.
- Автоматический rollback покрывает штатную ошибку процесса, но не гарантирует восстановление после отключения питания; для такого случая нужен описанный ручной откат и резервная копия.
- Не использовать старый VPS как рабочую площадку или цель деплоя: компоненты бота с него удалены.
